# Code2Pixel 设计与实现方案

这份文档把目前定下的 spec、从 [MiMo-V2.6 开源 RL 环境](https://huggingface.co/datasets/XiaomiMiMo/MiMo-V2.6-RL-oss)、[GAGAR](https://arxiv.org/abs/2609.32577) 和 [Automating eval design and hillclimbing](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) 里得到的启发，整理成可以照着做的方案。带"建议"的数字是初始值，试跑后再调。

## 1. 目标

- **测什么**：coding agent 只拿到一段文字，能不能用代码画出一张好图，和生图模型比。工具不限，只做静态图，禁止调用生图模型。
- **给谁用**：做后训练的模型公司。我们同时提供两样东西：
  - benchmark：隐藏的 test 集，用来报分；
  - RL 训练环境和训练数据：和 benchmark 共用同一套环境代码，但 test 集不进训练。
- **不做什么**：可交互场景、动画、3D 资产，也不 claim 已经比扩散模型画得好。

## 2. 任务定义

**输入**：一段文字，加上赛道和档位。

**输出**：agent 在 `/workspace` 里交三样东西，路径固定，校验要严格：

```
/workspace/out/final.png   最终图，尺寸由题目指定（默认 1536×1024）
/workspace/src/            生成它的全部代码
/workspace/run.sh          一条命令，在干净环境里从头重跑出 final.png
```

**赛道**

| 赛道 | 允许 | 禁止 |
|---|---|---|
| 主赛道 | 任何代码、任何渲染器（SVG、Canvas、Three.js、Blender、numpy……） | 联网；读现成图片、素材、模型；调用生图模型 |
| 素材赛道 | 另外可用环境里预置的授权素材库（照片、贴图、HDRI、3D 模型） | 联网；调用生图模型 |
| 辅助赛道 | 给一张参考图，用代码复刻 | 同主赛道 |

**harness**：直接用市面上用得最多的现成 agent，目前是 Claude Code 和 Codex，以后需要再加。不自己写 agent 循环。agent 在统一镜像里以 headless 模式运行，外层脚本（`harness/run.py`）负责起容器、监控预算、收集产出和记录。

**档位**：测的是一次正常调用、一轮长程运行的效果，也就是大家平时实际的用法。harness 不强制 agent 多试几轮，题目里也不要求用满预算：差模型多试很多次也能刷分，还会白白增加测试成本。

| 档位 | 规则 |
|---|---|
| 不看图 | 禁止查看任何图片（包括自己渲染的结果） |
| 正常运行 | 可以看图 |

- 两档的上限相同，都是 100 万 token、90 分钟，只用来防失控。超了直接停止，只保留已有文件。
- 结果报实际用量：token（原始数字全记）、时间、模型调用次数、看图次数。
- 阶段 1 验收时原本分低预算（20 万 token、30 分钟）和高预算（100 万、90 分钟）两档。两家 agent 都远没用满就自己停了（最多 13 万 token、22 分钟），所以合并成一档（见 [PHASE1.md](PHASE1.md)）。

**token 口径**：每次模型调用的"新增输入（不含缓存命中）+ 输出"累加。缓存读取不计入预算：每轮都会重读整个上下文，计进去的话预算会被轮数吃光，而且两家缓存机制不同，没法比。

## 3. 题库

**类别**：风景、街景、动物、人物、静物、多物体、指定画风（水墨、像素、动画背景等），外加一组"代码该赢"的题：

- 精确数量："桌上正好 7 个苹果"；
- 画面里的文字：招牌、题字、海报标题；
- 几何布局：对齐、对称、指定位置和比例；
- 精确修改：给一份已有的程序加一句修改要求，检查只有该改的区域变了。

**来源优先级**：

1. 人们真实让 coding agent 画图的 prompt，比如 X 上的 showcase，改写后使用，保留出处；
2. 人手写；
3. 以真实 prompt 为锚点的合成题。

**选题规则**：

- 题目的难度由人来判定，不按"当前模型做不好"来挑。那样测到的是某个模型的弱点，不是任务本身的难度。
- 所有模型、所有轮次都失败的题，人工复查，修改或删除。

**规模（建议）**：

| 集合 | 规模 | 公开 | 细则 | 用途 |
|---|---|---|---|---|
| train | 5,000+ | 公开 | 自动生成 | RL 训练 |
| dev | 150 | 公开 | 人工核对 | 报分、调试 |
| test | 300 | 不公开，每季度换一部分 | 人写 | 正式报分，不进训练 |

## 4. 评分

评分分三层。**第一层是门槛，不过门槛总分直接为 0。**

### 4.1 程序化规则（门槛）

- `final.png` 存在，可读，尺寸对；
- `run.sh` 在断网的新容器里重跑，结果必须和交上来的图逐像素相同，或只差多线程渲染带来的极小噪声（PSNR ≥ 50 dB，差超过 8 级的像素 ≤ 0.1%）（只拷代码，中间产物由 `run.sh` 重新生成）；
- 静态扫描加运行时检查，以下任何一项出现即判违规：
  - 嵌入位图（base64 data URI）；
  - 读取 `/workspace` 之外的图片或素材（素材赛道的素材库除外）；
  - 模型权重文件；
  - `diffusers`、`torch.hub` 等生图或预训练相关的 import；
  - 任何网络访问。
- 运行时检查用 strace：重跑时记录打开的文件和网络连接；agent 作答全过程也默认跟踪，作答时读了 `/workspace` 之外的图片同样判违规。实现和验证见 [PHASE2.md](PHASE2.md)。
- 题目里能用程序直接检查的约束，用程序判：比如指定背景色、画布比例，精确修改题里不该变的区域。

### 4.2 VLM 裁判

- **细则逐条判是或否，不打 1–5 分。** 每道题配 5–15 条能核对的具体说法，比如"画面里正好有 3 只猫""月亮在右上角""光从左边来"。每条独立判断，分数是通过的比例（可以加权）。
- 精确修改题：裁判同时看底稿图和交上来的图，细则里的“和原来一样”“原来的位置”按这个约定判；框外像素是否不变由门槛程序检查。
- **和固定图池两两比较。** 图池里放 2–3 个生图模型的同题图，加上参考 agent 的图。比较时隐去作者，两种顺序各判一次，抵消位置偏好。最后用 Bradley–Terry 算出 Elo，头条数字是"对最强生图模型的胜率"。
- **读代码（次要维度）。** grader 同时看代码：
  - 抓把像素数组硬编码进代码这类作弊，一经确认记为违规；
  - 给"可改、参数化"打分，单独报告，不计入主分。
- **judge 只看像素和代码，不看 agent 的自述。** 画面里写的字对 judge 来说只是像素，不是指令。

### 4.3 人工校准

- 上线前先人工读一批打过分的样本（建议 50 个），确认 judge 判的是对的。
- 每个题目类别收集人工盲评的两两比较（建议每类 200 对），公布三个一致率：VLM 与人的多数意见一致率、人与人之间的一致率、以及每条细则的一致率。
- 同一张图 judge 判两次、结论变化多的细则，改写或改由人工判断。

### 4.3b 细则当门槛，两两比较当主分（2026-10-02 用户定）

阶段 4 实跑里逐条细则得分接近满分（60 次里 52 次满分），分不出模型。原因是细则大多只核对"有没有"。所以改成：

- 细则分两种：**题目要求**（权重 2，`kind=requirement`）和**质量**（权重 1，`kind=quality`）。
- 题目要求细则当门槛：几遍判断取多数，加权通过比例达到 0.8 才算"满足题目"。
- 主分来自两两比较：门槛没过或题目要求没达标的一方直接判负，其余由裁判比；Bradley–Terry 算 Elo，bootstrap 给区间。
- 质量细则加了一批更难的说法，按类别加，精确修改题不加。得分单独报告，不进主分。一条细则有没有区分度，要用强弱不同的模型测；样本少、没测过弱模型时不删。
- 实现：`harness/score.py`。

### 4.4 训练 reward 和 benchmark 分数分开算

| | 训练 reward | benchmark 分数 |
|---|---|---|
| 比较对象 | 同题一组 rollout（建议 8 个），组内比较，顺序按 Williams 设计排 | 固定图池 |
| 组成 | 门槛 × 细则得分 × 组内相对名次 | 主分：对图池的两两比较 Elo 和胜率；门槛没过、或题目要求细则没达标的一方直接判负。质量细则得分单独报告 |
| 细则来源 | 自动生成 | 人写或人工核对 |

## 5. 评测本身要先过的检查

一个指标只有通过下面这些检查，才进入正式报分：

1. **分数随能力上升**：至少 3 个模型、各跑 2 个 effort 档，更强的模型、更高的 effort，分数要更高。
2. **留出区分空间**：最强模型开最高 effort，也要离满分很远（建议低于 70%）。试跑用的 CLIP 认对率第一轮就 12/12，就是没有区分空间的反例。
3. **噪声小于要关心的差距**：每题跑 3 个种子，用 bootstrap 算置信区间。区间半宽要小于打算据此下结论的最小差距（建议 2 分）。报分时附上置信区间。
4. **judge 稳定**：同一输出判两次，结论不一致的比例要低于 5%（建议值）。
5. **防刷分红队**：准备一批对抗样本，这些样本的得分必须是 0，或者至少不能比正常样本高：
   - base64 位图；
   - 画面里写"杰作""完美符合题意"之类的字；
   - 在画面里写 prompt injection；
   - 硬编码像素；
   - 偷偷调用模型。
6. **过拟合信号**：给使用者一条规则：dev 分数上升而 test 分数不动，说明过拟合了。我们自己的排行榜上同时显示 dev 和 test 两个分数。

## 6. 数据和环境格式

**每条任务一行**，格式参照 MiMo，可以直接接 verl 这类训练框架：

```json
{
  "prompt": [{"role": "user", "content": "…题目文字…"}],
  "reward_model": {
    "gate": {"size": [1536, 1024], "regen": "exact", "track": "main"},
    "claims": [{"text": "画面里正好有 3 只猫", "weight": 1}],
    "program_checks": [{"type": "background_color", "value": "#ffffff"}],
    "pairwise_pool": "pool-v1/0042"
  },
  "extra_info": {"task_id": "c2p-0042", "split": "dev", "track": "main", "budget": "6rounds",
                 "category": "动物", "source": "human", "docker_image": "code2pixel/env:0.1"}
}
```

**统一 Docker 镜像**（`env/Dockerfile`）：Python 科学计算栈、Node 加 Three.js、headless Chromium（Playwright）、Blender 4.0、rsvg、中文字体，外加 Claude Code 和 Codex 两个 CLI；自带 `c2p-render`，把 SVG 或 HTML（含 WebGL）渲染成 PNG。素材赛道额外挂载一个只读的素材库。

**网络**：agent 用订阅账号登录，必须能连模型服务。容器只接内部网络，通过出口代理（`env/proxy/`）上网，代理默认拒绝，只放行两家登录和模型调用的域名，并记录每个请求。

**代理管不到的地方，要在 agent 配置里关掉**：联网搜索、图像生成这些工具在模型服务端执行，请求不经过我们的代理。
- Codex：关掉 `image_generation`、浏览器、computer use、apps、插件，`web_search = "disabled"`，用 `--strict-config` 保证配置没写错；不看图档再关 `view_image`。
- Claude Code：禁用 WebSearch、WebFetch；不看图档禁止读取图片文件。
- 看图次数按工具输出里实际带回的图片数统计：Codex 可以在 `exec` 的代码里间接调用 `tools.view_image`，只数工具名会漏。

**卡住处理**：模型的流式回复偶尔会挂住。对话记录和会话记录连续 10 分钟没有新内容，判定为卡住并停止；批量运行时，卡住或一个 token 都没用就结束的，自动重跑一次，并在结果里标明。

## 7. 实现步骤

| 阶段 | 做什么 | 完成标准 |
|---|---|---|
| 0 | 试跑（已完成） | 24 张图、结论和局限都在报告里 |
| 1 | 环境和 harness：Docker 镜像、出口代理、`harness/run.py`（Claude Code、Codex）；用量计数和上限强制执行；日志 | 3 题 × 2 个 agent 跑通各档（已完成，见 [PHASE1.md](PHASE1.md)） |
| 2 | 门槛：输出路径校验、断网重跑比对、静态扫描、运行时检查、程序化约束 | 红队对抗样本全部被判 0；试跑 24 张里正常的全部通过（已完成：手写对抗样本 15/15 判不过；验收 18 次和试跑 A 赛道 12 张没有误判，B 赛道等素材规则定了再测。见 [PHASE2.md](PHASE2.md)） |
| 3 | 题库 v0：dev 150 题，带人工核对的细则；"代码该赢"类至少 30 题 | 每题有来源、类别和人判的难度（已完成 v0：常规 100 + 代码该赢 50，32 题改写自 X 上的真实 prompt；每题有来源、类别、难度、5–10 条细则，能程序判的约束写成门槛检查。细则由两个模型交叉检查，分歧和 30 题抽查按用户意见改由 subagent 审，还没有人逐条核对过；精确修改题的修改框用真实修改验证过。见 [PHASE3.md](PHASE3.md)） |
| 4 | VLM 裁判：逐条判细则；图池两两比较，含位置平衡和 Elo；读代码的 grader | judge 两次判定不一致的比例低于 5%（进行中：裁判自洽 98–100%、两个裁判逐条一致 92%；但细则得分接近满分、两两比较结论随裁判反转，等人工标注。见 [PHASE4.md](PHASE4.md)） |
| 5 | 生图模型基线：2–3 个生图模型画 dev 全部题，放进图池 | 图池覆盖 dev 全部题 |
| 6 | 验证评测：3 个模型 × 2 个 effort × 3 个种子；读 50 个样本；人工两两比较 | 第 5 节检查全部通过，不过的指标改完再测 |
| 7 | 训练环境：自动出题和自动生成细则，得到 train 集；组内比较 reward；导出 Parquet 和镜像 | 能用 verl 在 train 集上跑通一次小规模 RL，看到 dev 分数变化 |
| 8 | 发布：HF 数据集（train、dev）、镜像、评测代码、排行榜；test 集由我们来跑 | 报告给出分赛道、分档的分数、置信区间和成本 |

## 8. 还没定的问题

- VLM 裁判用哪个模型，是否用两个不同的模型交叉判。
- 生图模型基线用哪几个。
- 隐藏的 test 集怎么跑：模型公司给我们 API，由我们跑 agent；还是提供限时的评测窗口。
- 从 X 上收集的 prompt 怎么处理授权和出处。
- test 集的规模和更换频率。
